# Settings menu authored UI proof

This is the second UI-authoring proof for the **UI Authoring** CkTests gym. The implemented screen uses a code-created CommonUI activatable host containing one authored `main` region. The [HTML-like layout](../../../Resources/UiAuthoring/SettingsMenuProof/SettingsMenuProof.ui.html) supplies the hierarchy and bindings; the [stylesheet](../../../Resources/UiAuthoring/SettingsMenuProof/SettingsMenuProof.ui.css) supplies the geometry and visual states. The [generated reference](settings-menu-reference.png) is a visual target, never a runtime UI texture. Its exact [generation prompt](generation-prompts.txt) is retained for provenance. The focused Editor gate passed as recorded below.

The same gym's **[3] Inventory** screen extends the proof to authored image bindings, keyed cards, filtering, search and model-driven actions. Its complete breakdown is in [InventoryMenuProof](../InventoryMenuProof/README.md).

## Contract and component breakdown

The logical reference viewport is **1920 × 1080**. A centered **960 × 776** card begins at **(480, 152)**, with **56** units of padding, radius **16**, fill `#182129F5`, and a 1-unit `#56616A` border. These are normalized design targets, not measurements extracted from the generated image. A dimmed alpine lake is reference scenery; the form must remain a live native UI. The authored `settings-composition` root has no fixed sizing properties, allowing the host to provide the viewport slot. Its `settings-top-space` and `settings-bottom-space` center the card vertically around the hint.

The document contains one root under `<region name="main">`; every ID is unique. Text-bearing IDs are typed `<text bind="...">` elements. The checkbox label is separately authored text, so it has no `label-bind`. The `DisplayModes` options use stable keys `Windowed`, `Borderless`, and `Fullscreen` with display labels supplied by the native collection. Layout and stylesheet references are plugin-relative. Authored CSS styles the slider, checkbox, and select. On a compatible reload, those native controls and an open select popup are retained while ordinary action buttons are replaced; an invalid reload leaves the entire accepted view and draft intact.

## State and input contract

On the first open, committed and draft values are **75**, **true**, and **Windowed**. The status reads **No changes**, and Apply is disabled. A slider gesture may preview `VolumeValue` through `PreviewVolume`; `EditVolume` commits the finite proposed value to the draft, and canceling a gesture clears its transient preview. Only a committed draft difference enables Apply. Checkbox and select changes edit the draft. In the generated reference pose, selecting **Borderless** makes the form dirty, changes status to **Unsaved changes**, enables Apply, and places keyboard focus on Apply. Apply copies the draft into the gym PlayerController's in-memory committed state and leaves the Settings form open. Reopening Settings in that gym session shows the committed values. This proof must not write system audio volume, display mode, or machine preferences.

The gym exposes **[1] Pause menu** and **[2] Settings**. Cancel or Esc discards the draft; if Settings was entered from Pause, it returns to Pause, otherwise it closes the preview. Switching views releases the prior authored popup and input capture. When a menu is active, Tab belongs to its native focus navigation and must not open the gym selector; H and numbered panel shortcuts must not leak through the menu. Closing the preview restores the gym's existing panel state and pause ownership.

## Acceptance and known visual gaps

Acceptance requires live, focusable native controls and correct slider/checkbox/select callbacks; clean/dirty/Apply/Cancel behavior; state persistence within one gym PlayerController; reload rejection without a partial view; lifecycle cleanup after replacement and PIE end; readable card and controls without clipping at 1280 × 720, 1920 × 1080, and 2560 × 1080; and keyboard navigation that does not trigger gym shortcuts. Visible labels use live native `FText`; screen-reader names and verification are deferred, along with physical gamepad input, dynamic input glyphs, multi-user ownership, and packaged Windows execution.

The generated reference paints the volume track amber up to 75%; the native slider style colors its bar uniformly. The slider and closed dropdown retain Slate's default blue keyboard-focus decoration. The native dropdown popup uses gray Slate menu styling; the reference shows only the closed dropdown, so it provides no open-popup visual target. These are explicit visual differences in the live controls.

The checkbox now matches the reference's amber box and ivory check through separate `-ck-checkbox-background-color` and `-ck-checkbox-checked-color` declarations. This engine's Starship style paints a separate background and has no unchecked image; tinting only its unchecked image could not change the box. The new background property covers its normal, hovered and pressed brushes. Other engine styles that combine box and check art may still limit independent coloring.

The selected host's [EditorEngine configuration](../../../../../Config/DefaultEngine.ini) enables frame-rate smoothing with an inclusive 5–30 FPS range. This caps fast Editor frames, including PIE in that process, without enabling a fixed timestep or changing packaged GameEngine settings. The Settings test checks the configured upper bound and `GEditor->GetMaxTickRate(1/120)` after startup, because the earlier `t.MaxFPS` setting was overwritten by Editor initialization.
